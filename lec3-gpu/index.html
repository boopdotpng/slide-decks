  • the caches on the map help, but they're far too: 32 KB per compute unit, 8 MB and 64 MB for the whole chip

part 2 · the code

the kernel: what one pixel does

hip: c++ with a few extra words. this is the whole of brighten

__global__ void brighten(unsigned char *img, unsigned n, unsigned a) {
  unsigned i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) {
    unsigned p = img[i] * a;
    img[i] = p < 255 ? p : 255;
  }
}
  1. __global__: this function runs on the gpu. you never call it once: you ask for a grid, and every thread runs it
  2. which pixel is mine? block number × 256 + my number in the block. the hardware hands every thread its two numbers. there's no loop and no i++
  3. if (i < n): a photo's size needn't be a multiple of 256, so the last block can stick out past the end. those threads get switched off: the exec mask
  4. the body: what one pixel does. read it, multiply, cap at 255 (white), write it back. the same few lines as the cpu loop's body
shadows: the branch from the wave slides is just an if. which lanes take it is decided per pixel, at run time
__global__ void shadows(unsigned char *img, unsigned n) {
  unsigned i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) {
    unsigned p = img[i];
    if (p < 40) img[i] = p * 2;
  }
}
part 2 · the code

the whole program

the kernel is the only part that runs on the gpu. the rest is an ordinary cpu program

#include <hip/hip_runtime.h>
#include <vector>
 
__global__ void brighten(unsigned char *img, unsigned n, unsigned a) {
  unsigned i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) {
    unsigned p = img[i] * a;
    img[i] = p < 255 ? p : 255;
  }
}
 
int main() {
  const unsigned n = 12'000'000;            // a 12 megapixel photo, one byte per pixel
  std::vector<unsigned char> img(n);        // (reading the photo from a file: left out)
 
  unsigned char *gimg;
  hipMalloc(&gimg, n);
  hipMemcpy(gimg, img.data(), n, hipMemcpyHostToDevice);
 
  const unsigned block = 256, blocks = (n + block - 1) / block;
  brighten<<<blocks, block>>>(gimg, n, 2);
 
  hipMemcpy(img.data(), gimg, n, hipMemcpyDeviceToHost);
  hipFree(gimg);
}
  1. the kernel, the same as the last slide. the only part the gpu runs
  2. main runs on the cpu. the photo starts in ram, where the gpu can't see it: a kernel has no instruction that reaches ram
  3. hipMalloc: room in the gpu's 16 GB. the pointer is only good for handing to the gpu
  4. hipMemcpy: copy the photo ram → gpu memory, 12 MB
  5. the launch: how many blocks, how many threads in each, then the arguments. 46,875 blocks × 256 = one thread per pixel. it returns at once: the gpu works while the cpu carries on
  6. copy the answer back. this one waits for the kernel to finish first
  7. free. build it with hipcc brighten.cpp. in cuda it's the same program with cuda where it says hip
part 2 · the code

what a launch does

1 · compile
hipcc builds a normal cpu program with the gpu's instructions packed inside it
2 · launch
hip's runtime writes the arguments into memory the gpu can read, and fills in a 64-byte packet
3 · queue
the packet goes into a ring of packets in memory the gpu can read. then one write to a device register: the doorbell
4 · the gpu
its command processor reads the packet, walks the grid, and starts waves on the wgps with their registers filled in
5 · done
when the last wave ends, the gpu flips a signal in memory. whoever was waiting on the cpu wakes up
the packet for brighten<<<46875, 256>>>(gimg, n, 2)

the obvious kernel is wrong

__global__ void hist_naive(unsigned *bins, const unsigned char *img, unsigned n) {
  unsigned i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) bins[img[i]]++;                     // read, add 1, write: three steps
}
read bins[p]→add 1→write bins[p]
one thread per pixel: add 1 to the counter for my brightness. it looks right. but ++ on memory is three steps: read the counter, add 1 in a register, write it back
part 3 · threads that cooperate

fix 1: let the cache do the add

__global__ void hist_atomic(unsigned *bins, const unsigned char *img, unsigned n) {
  unsigned i = blockIdx.x * 256 + threadIdx.x;
  if (i < n) atomicAdd(&bins[img[i]], 1);
}
thread a+1 →
thread b+1 →
bins[20], in the shared cache: one add at a time
41a's +142b's +143
atomicAdd: send "+1" out to the chip's shared cache (the 8 MB one), and it does read, add, write as one step. nobody can cut in between. two adds to the same counter take turns
part 3 · threads that cooperate

fix 2: count nearby, then add once

__global__ void hist_lds(unsigned *bins, const unsigned char *img, unsigned n) {
  __shared__ unsigned local[256];                // one copy per block, in lds
  unsigned t = threadIdx.x;                      // 256 threads, 256 bins: bin t is mine
  local[t] = 0;
  __syncthreads();                               // wait: every bin is cleared
  for (unsigned k = 0; k < 16; k++) {
    unsigned i = (blockIdx.x * 16 + k) * 256 + t;
    if (i < n) atomicAdd(&local[img[i]], 1);     // near: lds
  }
  __syncthreads();                               // wait: every pixel is counted
  atomicAdd(&bins[t], local[t]);                 // far: one add per bin per block
}
block 1: 256 threads = 8 waves
wave 0startingwave 1startingwave 2startingwave 3startingwave 4startingwave 5startingwave 6startingwave 7starting
lds: local[0 … 255], whatever was left there
↓ 256 adds, one per thread, into the real counters (dashed: what all blocks add up to)
each block gets its own 256 counters in lds: inside the workgroup processor (~20 ns), and only this block's 256 threads can touch them. 256 threads, 256 bins: bin t is thread t's

what we covered, and what it means for your code

the modelwrite what one pixel does, ask for a thread per pixel. 32 threads make a wave (one instruction for all of them), up to 1024 threads a block (one wgp, shared lds), every block a grid
memory is fargpu memory is ~100 adds away. a simd parks many waves and runs whichever is awake: use few registers, launch plenty of threads
branchesa wave has one pc. an if its threads disagree on runs both ways with lanes switched off: keep neighbouring pixels doing the same thing
sharing a counterbins[p]++ from thousands of threads loses counts. atomicAdd is right, but every add makes the trip across the chip and queues at the shared cache
cooperating cheaplycount inside the block in lds, with barriers between the phases, then one far add per bin. blocks can't wait for each other: only threads in a block can
the programcopy in, launch, copy out. the gpu can't see ram
